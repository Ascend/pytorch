# 原生 API 格式与写作规范

本规范制定于2026年10月。

## 1. 先区分页面类型

| 页面 | 写法 |
| --- | --- |
| `pytorch_<版本>/torch*.md` 等模块参考页 | 页面说明、可选目录、分类标题、API 条目 |
| `overview.md` | 本版本支持清单的范围和说明，不强加 API 条目结构 |
| `PyTorch-*.md`、`_menu_pt_native_apis.md` | 版本入口或导航，沿用实际菜单约定 |
| 入图、DTensor、确定性、私有 API 清单和附录 | 保留各自列表、表格或操作说明，不批量改为产品支持条目 |

## 2. 模块页面结构

API 模块及子标题的名称、层级结构和排列顺序必须对齐对应版本的上游 PyTorch 文档，页内目录与正文同步保持一致。保留上游标题名称，不自行翻译、重命名、合并分类或按字母、产品、支持状态重新排序。核对时使用目标版本的模块或专题页面，不以其他版本或 latest 页面代替。产品支持字段、限制说明及站点 HTML 包装采用本仓库格式，不要求上游也具有这些字段。

通常依次为：一级模块标题、NOTE 提示、HTML 目录容器、隐藏模块标题、分类及条目。

- 一级标题使用实际模块名称，例如 `# torch.nn.functional`。
- NOTE 说明限制与说明的意义、未收录 API 尚未验证、产品范围及上游模块链接。编辑现有页面时保留已有说明；新页面从同版本相近模块取得结构并调整链接，不抄错版本。
- 目录容器保留现有 `div` 样式和内部目录标题。目录条目指向分类标题，保留原有层级及锚点规则。
- 形如以下的隐藏标题属于页面结构，不当作多余标题删除或删除零宽字符实体：

```html
<div style="display:none;">

## &#8203;torch.nn.functional

</div>
```

- 分类通常用二级标题，API 条目通常用三级标题。已有类和方法可能带 `_`、`class` 或 HTML 修饰，按目标页面保留，不一律改成普通函数标题。
- API 条目内部用字段标签，不再增加与下一条 API 同级的标题。

## 3. API 条目结构

下面是结构示意，尖括号占位内容须替换；它不表达任何实际 API 的支持结论。

```markdown
### <API 全限定名>

<div style="margin-left: 2em">

**原生文档**：[<API 名称>](<已核实的对应版本链接>)

**产品支持情况**：

<!-- npu="910b" id<本文件未使用的编号> -->
- <term>Atlas A2训练系列产品</term>：<已验证的支持状态>
<!-- end id<同一编号> -->
<!-- npu="A3" id<另一个未使用的编号> -->
- <term>Atlas A3训练系列产品</term>：<已验证的支持状态>
<!-- end id<同一编号> -->
<!-- npu="950" id<另一个未使用的编号> -->
- <term>Ascend 950DT系列产品</term>：<已验证的支持状态>
<!-- end id<同一编号> -->

**限制与说明**：

- <有依据的限制或差异>

</div>
```

- 字段顺序为原生文档、产品支持情况、可选的限制与说明。没有限制信息时省略整个限制字段，不填“无”或留空占位。
- 一条短限制可与字段同行：`` **限制与说明**： `input`仅支持fp16，fp32 ``。多条限制改为字段后空行接列表。
- 不把原生接口重新写成“功能描述、参数、返回值”的完整手册；使用方法通过原生文档链接提供。
- 代码围栏、列表、HTML 容器前后保留合理空行，避免 Markdown 被当成 HTML 内的普通文本。

## 4. 产品支持列表与条件注释

产品筛选标签用于按产品筛选展示信息，按行使用，不支持行内标签。开始注释和结束注释分别独占一行，需筛选的正文放在两者之间；不能在一句话、一个列表项或表格单元格中插入标签来筛选其中一部分。这里指 `<!-- npu="..." id... -->` / `<!-- end id... -->`，不要求 `<term>` 产品名称标记独占一行。

正确示例：

```markdown
<!-- npu="910b" id1 -->
- <term>Atlas A2训练系列产品</term>：支持
<!-- end id1 -->
```

错误示例（不支持行内筛选）：

```markdown
- 产品支持情况：<!-- npu="910b" id1 --><term>Atlas A2训练系列产品</term>：支持<!-- end id1 -->
```

同一句含多个产品的不同限制且需要分别筛选时，拆成各自完整的行或列表项，再分别包裹标签；保留共有条件和原有语义。

当前样本映射为 `910b` → Atlas A2训练系列产品、`A3` → Atlas A3训练系列产品、`950` → Ascend 950DT系列产品。大小写有意义；未来产品从目标分支样例或处理工具确认，不自行发明编码。

- 每个开始注释和结束注释必须使用相同 ID。编辑现有条目不改已有 ID，不移动注释边界以扩大或缩小作用范围。
- 新增块先扫描整份文件的已有 ID，分配未使用的编号；不要复制邻近条目 ID。现有样本按文件编号，检查同文件冲突；若仓库工具另有范围要求，以工具为准。
- 三个产品状态分别写在各自块内，不为了压缩篇幅合并为一行。支持和不支持都应保留已验证的产品记录。
- `<term>` 是产品名称的结构标签，保留。既有名称可能存在空格或后缀差异；文字润色不批量替换产品术语。
- 已存在的无注释列表不自动补齐标记；新增条目优先采用同页主流结构。历史支持表的迁移仅在用户明确要求时进行。
- 若目标页在限制正文也使用条件注释，保留原本范围及列表层级。没有条件注释的产品专属限制，要在句首明确适用产品，不能因支持列表已有筛选块就假定正文也会被筛选。
- 没有找到发布处理工具时，只能确认注释结构，不声称已验证产品筛选后的渲染结果。

## 5. 限制与说明的表达

### 参数、dtype 和取值

- 参数名、属性名、API 名和代码表达式使用反引号；`True`、`False`、`None` 和模式字符串按代码值表达。
- 限制应明确对象。函数不默认全写 `input`；Tensor 方法可涉及 `self`；创建 API 可涉及 `dtype`；多输入 API 按实际对象分别写。对象不明确时核实签名及支持证据，不能仅靠第一个参数猜测。
- dtype 沿用本版本的原有集合和命名，不统一扩展成 `torch.*`，不从其他版本复制或去重跨参数限制。
- “仅支持”用于明确的完整范围；原文只是“支持”时不能机械加入“仅”。
- 保留原数值和单位。将双重否定改为正面约束时，核对不等式方向、整除关系、边界是否包含及多个条件的逻辑关系。
- 不把“可能回退”改成“一定回退”，不把精度差异改成错误，不添加未经验证的实现原因。

### 简单与复杂条目

简单条目一条限制写一项，例如“`input`仅支持1-8维”。复杂条目可按输入规格、参数组合、执行模式、原生差异和规避方法分组，只使用确实需要的组。

例如 SDPA 条目有多输入 dtype、布局、head 数关系、维度范围、mask 与 causal 组合、后端设置及原生差异。应保留其层级，用父项表达共同条件、子项表达具体约束，不扁平化为一长段，也不要求每个 API 都有这些组。

- 同一个父项内的约束默认容易被理解为同时成立；有“或”的情形显式写清。
- 与产品、dtype、正反向或执行模式有关的限定语应靠近对应限制。
- 重复描述只有在对象、条件和技术结论完全相同时才可合并；看似重复的不同参数限制分别保留。
- 复杂限制不新增四级标题来打乱条目结构，优先采用列表和加粗分组标签。

## 6. 示例

当示例能展示开关配置、上下文、参数组合或已验证的规避操作时添加。纯 dtype 清单、范围声明和精度风险通常用文字即可，不为满足模板强加代码。

- 在引出示例的列表项内缩进代码块；开闭围栏一致，使用 `python` 等实际语言标记，围栏前后空行。
- 新增示例包含必要导入、前置配置和输入定义；若只提供操作片段，明确哪些输入由调用方准备，不能称为可独立运行示例。
- 代码需符合本条目的版本、支持产品、dtype、shape 和执行模式。上游示例不能直接证明 NPU 示例有效。
- 设置开关的示例应在相应操作前设置；涉及全局行为时说明其已知作用范围，不猜测生效时机。
- 可以改善既有示例的导入和格式，但不凭格式改写技术路径。缺少 NPU 运行环境时静态核对，不报告运行通过。

## 7. 版本、链接和导航

- 展示范围与对应版本的上游 PyTorch 保持一致：上游已废弃或不再展示的模块、分类和 API，本清单也不展示。维护展示范围时移除对应正文条目，并同步清理相关页内目录及导航入口；不能因旧链接仍可访问就继续保留展示。以目标版本上游的废弃说明和展示情况为依据，不能仅凭链接访问失败判定，也不将新版本的变化套到历史版本。
- 目录如 `pytorch_2-14-0` 对应页面版本 2.14.0；当前常见 PyTorch 文档 URL 使用 `/docs/2.14/`。使用目标 API 的实际链接，不机械拼接。
- 类方法、模块入口、torchvision 等外部模块可能采用特殊 URL 或锚点，逐项确认需要修改的链接。已废弃接口按展示范围规则处理，不通过修复链接继续展示。
- Named Tensors 等专题中的条目应链接到对应专题页面及锚点，不能按显示的 API 名改成普通 API 链接。例如现有 2.11 文档中，Named Tensors 的 `torch.Tensor` 指向 `named_tensor.html#named-tensors`，`torch.Tensor.names` 指向 `named_tensor.html#torch.Tensor.names`；不要替换为 `generated/torch.Tensor.html`、`generated/torch.Tensor.names.html` 或普通 Tensor 参考页。其他版本核对该版本实际专题路径及锚点，不机械复制这些示例。
- 同名 API 在不同专题中的链接可以不同；核对链接时同时考虑所在专题和目标说明，不仅比较 API 名称。批量链接修复也遵循此规则。
- 新增 API 放入对应版本上游的分类和相对位置，模块及子标题的名称、结构和顺序与上游一致；增加或调整分类、页面时同步更新涉及的目录或导航，不强制给每个 API 加页内目录项。
- 新增版本需检查版本入口、概述和总菜单；不能仅批量替换版本号后宣称支持事实一致。
- 不把未收录、未验证与不支持混为一谈。入图、DTensor 和确定性支持是独立能力，不能从普通产品支持状态推导。

## 8. 最小验收

文字润色：审阅 diff，确认事实、产品块、ID、链接和标题锚点保留。新增条目：核对证据、字段顺序、容器闭合、ID 不冲突、分类位置和相关导航。结构迁移：额外检查迁移前后每个 API 的产品状态和限制归属。

验证应按具体修改范围进行，不因仓库存在历史告警就改动无关页面。区分静态结构检查、文档工具检查、站点渲染和 NPU 示例运行，并据实报告完成了哪些。
