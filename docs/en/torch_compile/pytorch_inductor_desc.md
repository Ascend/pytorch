# Inductor

## Overview

Inductor is the default backend compiler for `torch.compile()`. Through the collaborative approach of "Dynamo frontend graph capture + Inductor backend optimization + high-performance operator generation," it automatically performs operator fusion and code generation without altering the model logic, significantly improving training or inference throughput.

The Inductor backend supports three operator compilers, which can be selected based on the scenario:

| Compiler | Mode | Enabling Method | Description |
| - | - | - | - |
| Triton | Default mode |`torch.compile(backend="inductor")`| Generates fused operators based on Triton. This is the default choice for the Inductor backend and is suitable for most scenarios. For a detailed introduction, see the [Triton-Ascend Official Repository](https://gitcode.com/Ascend/triton-ascend).|
| Torch-MLIR | MLIR mode |`torch.compile(backend="inductor", options={"npu_backend": "mlir"})` | Generates fused operators based on Torch-MLIR. For a detailed introduction, see the [Torch-MLIR Official Repository](https://github.com/llvm/torch-mlir).<br><term>Ascend 950DT</term> does not currently support MLIR mode.|
| DVM | DVM mode |`torch.compile(backend="inductor", options={"npu_backend": "dvm"})` | Generates fused operators based on DVM. For a detailed introduction, see the [DVM Official Repository](https://gitcode.com/mindspore/dvm/tree/master).|

> [!NOTICE]
>
> Install Triton Ascend v3.2.2 before using the inductor backend.For details, see [Triton Ascend Installation Guide](https://triton-ascend.readthedocs.io/en/v3.2.2/installation_guide.html).<br>
> When using MLIR mode or DVM mode, the Inductor backend requires an additional Torch-MLIR dependency package, which can be downloaded from the [Torch-MLIR Archive](https://repo.oepkgs.net/ascend/pytorch/vllm/torch/).<br>
> Before importing torch, you can also select the compiler mode via the `TORCHINDUCTOR_NPU_BACKEND` environment variable. For details, see [TORCHINDUCTOR_NPU_BACKEND](../environment_variable_reference/TORCHINDUCTOR_NPU_BACKEND.md).

## Compiler

### Triton (Default Mode)

Triton is the default operator compiler of Inductor. While retaining the core logic of torch.compile's dynamic graph capture + static graph optimization + efficient code generation, it leverages Triton's automatic Tiling and fused-operator generation capabilities to significantly reduce the workload of manual Tiling design and memory management, improving performance by reducing the number of memory accesses.

The Triton Compiler includes the following core Components:

| Component | Positioning | Function |
| - | - | - |
| Inductor-Triton | Core compiler (fused operator generator) | Automatically generates high-performance fused operators based on Triton-Ascend. Through strategies such as operator fusion, data type optimization, and computation graph simplification, it balances compilation flexibility and optimization depth. |
| Triton CodeGen | Code generator (hardware-aware code generator) | Receives the optimized computation graph and generates dedicated high-performance low-level code for the target hardware (NPU), automatically completing Tiling and shared memory management. |

#### Call Example

```python
import os
os.environ['TORCHINDUCTOR_NPU_BACKEND'] = 'default'

import torch
import torch_npu
from torch._inductor.utils import run_and_get_code

# Define the model
def op_calc(x, y):
    return x * y

x = torch.randn((3,), requires_grad=False, dtype=torch.float32, device="npu")
y = torch.randn((3,), requires_grad=False, dtype=torch.float32, device="npu")
std_out = op_calc(x, y)

compile_func = torch.compile(op_calc, backend="inductor")
compile_out, codes = run_and_get_code(compile_func, x, y)
print(codes[0])
```

#### Output Triton Fused Operator

After Triton compilation, Fused Operator code is generated internally, which can be viewed through `codes[0]`:

```python
def call(args):
    arg0_1, arg1_1 = args
    args.clear()
    with torch.npu.utils.device(0):
        torch.npu.set_device(0)
        buf0 = empty_strided((3, ), (1, ), device='npu', dtype=torch.float32)
        # Topologically Sorted Source Nodes: [mul], Original ATen: [aten.mul]
        stream0 = get_raw_stream(0)
        triton_poi_fused_mul_0.run(arg0_1, arg1_1, buf0, 3, stream=stream0)
        del arg0_1
        del arg1_1
    return (buf0, )
```

Here, `triton_poi_fused_mul_0` is the core execution interface generated by Triton compilation, which executes the fused operator computation on the specified NPU device and compute stream.

### MLIR

As an extended upgrade of the Inductor backend, Inductor-MLIR retains the core logic of torch.compile's dynamic graph capture + static graph optimization + efficient code generation, while leveraging MLIR's multi-level, cross-architecture compilation capabilities to adapt to the deep optimization requirements of various hardware architectures, significantly improving compilation flexibility and performance ceilings for model training and inference across different computing platforms.

The Inductor-MLIR compiler includes the following core components:

| Component | Positioning | Function |
| - | - | - |
| Inductor-MLIR | Core compiler (multi-level IR optimizer) | Converts FX Graph into MLIR multi-level Intermediate Representation (IR), and through cross-level optimization strategies (such as operator splitting and fusion, data type optimization, and computation graph simplification), balances compilation flexibility with optimization depth to adapt to the compilation characteristics of different hardware. |
| MLIR CodeGen | Code generator (hardware-aware code generator) | Receives the optimized MLIR IR and generates dedicated high-performance low-level code for the target hardware. |

#### Call Example

```python
import os
os.environ['TORCHINDUCTOR_NPU_BACKEND'] = 'mlir'

import torch
import torch_npu
from torch._inductor.utils import run_and_get_code
import torch_npu._inductor

# Define the model
def op_calc(x, y):
    return x * y

x = torch.randn((3,), requires_grad=False, dtype=torch.float32, device="npu")
y = torch.randn((3,), requires_grad=False, dtype=torch.float32, device="npu")
std_out = op_calc(x, y)

compile_func = torch.compile(op_calc, options={"npu_backend": "mlir"})
compile_out, codes = run_and_get_code(compile_func, x, y)
print(codes[0])
```

#### Output MLIR Fused Operator

`codes` is the captured MLIR output code snippet, which contains the `call` function and the `benchmark_compiled_model` function. The `call` function internally encapsulates the operator logic generated by MLIR compilation:

```python
def call(args):
    arg0_1, arg1_1 = args
    args.clear()
    with torch.npu.utils.device(0):
        torch.npu.set_device(0)
        buf0 = empty_strided((3, ), (1, ), device='npu', dtype=torch.float32)
        stream0 = get_raw_stream(0)
        mlir_fused_mul_0.run(arg0_1, arg1_1, buf0, stream=stream0)
        del arg0_1
        del arg1_1
    return (buf0, )
```

Here, `mlir_fused_mul_0.run` is the core execution interface generated by MLIR compilation, which executes the fused multiplication operator computation on the specified NPU device and compute stream. It receives input tensors and writes the computation results to output tensors, serving as the underlying implementation of the original multiplication logic optimized by MLIR.

### DVM

DVM is an optional operator compiler of Inductor, which generates fused operators based on DVM.

DVM currently supports two fusion modes: `mlir_fusion` and `graph_fusion`, corresponding to two strategies: reusing Inductor-MLIR fusion results and custom graph fusion paths, respectively.

| Mode | Depends on Inductor MLIR | Pattern Control | Applicable Scenario |
| - | - | - | - |
| mlir_fusion | Yes | Low | Reuse Inductor fusion results |
| graph_fusion | No | High | Custom/Complex/Experimental fusion | 

#### Call Example

```python
import os
os.environ['TORCHINDUCTOR_NPU_BACKEND'] = 'dvm'

import torch
import torch_npu
import torch_npu._inductor

# mlir_fusion mode
torch._inductor.config.npu_backend = "dvm"

# Define the model
def op_calc(x, y):
    return x * y

x = torch.randn((3,), requires_grad=False, dtype=torch.float32, device="npu")
y = torch.randn((3,), requires_grad=False, dtype=torch.float32, device="npu")

# Compile and execute
compile_func = torch.compile(op_calc, backend="inductor", options={"npu_backend": "dvm"})
out = compile_func(x, y)
```

#### Output DVM Fused Operator

After DVM compilation, the corresponding fused operator code is generated. The output examples for the two modes are as follows:

**mlir_fusion mode output:**

```python
# Declare the operator
@dvm.kernel(ktype='vector', dyn_shape=True)
def dvm_fused_add_mul_sum_0_build(k):
    arg0_1 = k.load([-1, 1], torch.bfloat16)
    arg1_1 = k.intref()
    arg2_1 = k.intref()
    arg3_1 = k.intref()
    arg4_1 = k.view_load([-1, -1, -1], [-1, -1, 1], torch.bfloat16)
    arg5_1 = k.load([1, -1], torch.bfloat16)
    expand = k.broadcast(arg0_1, [arg1_1, arg2_1, arg3_1])
    mul = k.mul(expand, arg4_1)
    expand_1 = k.broadcast(arg5_1, [arg1_1, arg2_1, arg3_1])
    add = k.add(mul, expand_1)
    _npu_dtype_cast = k.cast(add, torch.float32)
    sum_1 = k.sum(_npu_dtype_cast, [0, 2], True)
    k.store(sum_1, torch.float32)
    k.set_kernel_info(
        'dvm_fused_add_mul_sum',
        'dvm_fused_add_mul_sum_0',
        [True, True, True, True, True, True, True],
    )

# Use
buf2 = empty_strided((1, s0, 1), (s0, 1, s0), device='npu', dtype=torch.float32)
stream0 = get_raw_stream(0)
dvm_fused_add_mul_sum_0.run(arg4_1, s1, s0, s2, buf1, arg5_1, buf2, stream=stream0)
```

**graph_fusion mode output:**

```python
# Declare the operator
@dvm.kernel(ktype='split', dyn_shape=True)
def dvm_graph_fused_0(k):
    arg4_1 = k.load([-1, 1], torch.bfloat16)
    permute = k.view_load([-1, -1, -1], [-1, -1, 1], torch.bfloat16)
    mul_3 = k.mul(arg4_1, permute)
    arg5_1 = k.load([1, -1], torch.bfloat16)
    add_8 = k.add(mul_3, arg5_1)
    convert_element_type_default = k.cast(add_8, torch.float32)
    sum_1 = k.sum(convert_element_type_default, [0, 2], True)
    convert_element_type_default_1 = k.cast(sum_1, torch.bfloat16)
    k.store(convert_element_type_default_1, torch.bfloat16)

# Use
buf0 = dvm_graph_fused_0(arg4_1, reinterpret_tensor(arg3_1, (s1, s0, s2), (s2, s1*s2, 1), 0), arg5_1)
```

## Compilation Mode

`mode="reduce-overhead"` is an optimization strategy for reducing overhead. Its core logic corresponds to **NPUGraph Tree**:

- **Dynamic Shape Routing**: Manages multiple related NPUGraphs, allowing the optimization benefits of NPUGraph to cover dynamic shape scenarios, rather than being limited to fixed shapes.
- **Subgraph Memory Optimization**: Optimizes memory usage across multiple subgraphs in segmented graph scenarios.
- **Working Principle**: Under multiple inputs of different shapes, the Tree caches multiple captured graph versions and automatically routes to the best-matching subgraph for replay based on the input shape.

For more details, see [CUDAGraph Trees](https://docs.pytorch.org/docs/stable/user_guide/torch_compiler/torch.compiler_cudagraph_trees.html).

Example of enabling NPUGraph Tree logic:

```python
compiled_model = torch.compile(
    model,
    backend="inductor",
    mode="reduce-overhead"  # Enable NPUGraph Tree logic
)
```

## Compilation Options

Compilation options supported by Inductor (the `options` parameter):

| Option | Description |
| - | - |
| `triton.cudagraphs` | Triton-related configuration |
| `trace.enabled` | Trace toggle |
| `enable_shape_handling` | Shape handling configuration |
| `npu_backend` | Specifies the operator compiler (`"mlir"` or `"dvm"`, default Triton) |

## Constraints

1. The optimizer is typically not captured in the graph. The optimizer's `step()` involves Python-side dynamic logic (such as learning rate scheduling, gradient accumulation, and adaptive update rules), which is difficult for a static graph to capture.
2. `torch.compile(backend="inductor")` supports dynamic shapes, but it triggers recompilation (increasing overhead). You are advised to keep shapes fixed whenever possible.
